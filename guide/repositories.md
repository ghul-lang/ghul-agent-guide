# The repositories

Everything lives under [github.com/ghul-lang](https://github.com/ghul-lang).
Every repository that builds ghūl code pins its tools, the compiler included,
in `.config/dotnet-tools.json`, so **`dotnet tool restore` comes first** in
each of them. All of them need the .NET 10 SDK; the few that need more say so
below. Where a repository has its own `AGENTS.md`, read it before changing
anything there.

"Publishes" means a merge to `main` releases a package, whose version is
chosen as [versioning.md](versioning.md) describes; those repositories carry
a `VERSION` file.

## The compiler and its libraries

**`ghul`** - the compiler, written in ghūl and compiled by its own previous
release. Publishes `ghul.compiler` to NuGet, consumed as a local .NET tool
(`dotnet ghul-compiler`). Also home of
[`GHUL.md`](https://github.com/ghul-lang/ghul/blob/main/GHUL.md), the
language reference. Merges through a merge queue.

```sh
dotnet tool restore
dotnet tool update --local ghul.compiler     # build with the latest release, as CI does
dotnet build
dotnet test unit-tests
dotnet publish --output publish/             # before the next two
dotnet ghul-test integration-tests
dotnet ghul-test --use-dotnet-build cross-assembly-tests
dotnet test analysis-tests
./build/bootstrap.sh                         # self-hosting check
```

Read [compiler.md](compiler.md) before changing it.

**`ghul-runtime`** - the runtime library every ghūl program links: the pipe
combinators, collections support, display, and the MSBuild targets that build
ghūl projects. Publishes `ghul.runtime`.

```sh
dotnet tool restore
dotnet test tests/tests.ghulproj
```

Its CI also builds and runs a small integration project. `GHUL.md` belongs to
the compiler repository; link to it rather than copying it here.

**`ghul-test`** - the snapshot-based integration test runner (`dotnet
ghul-test`) the other repositories use. Publishes `ghul.test`.

```sh
dotnet tool restore
dotnet build
dotnet test tests/tests.ghulproj
integration-tests/run-integration-tests.sh
```

A test directory is recognised by its `ghulflags` file; a directory that looks
like a test but has none fails the run rather than being skipped.

**`ghul-raster`** - a pure-managed PNG drawing library that also works under
WebAssembly. Publishes `ghul.raster`.

```sh
dotnet tool restore
dotnet test unit-tests
dotnet build
dotnet ghul-test --use-dotnet-build integration-tests
```

`src/font-data.ghul` is generated by `build/embed-font.sh`; regenerate it
rather than editing it.

## Tools

**`ghul-vsce`** - the VS Code extension (marketplace `degory.ghul`), and the
standalone language server published to npm as `@ghul/language-server`. Needs
Node.js.

```sh
npm install
npm test
npm run test:integration     # also needs the .NET SDK
```

It talks to the compiler's analysis mode, so a breaking protocol change in
the compiler needs a matching change here.

**`ghul-mcp`** - an MCP server exposing semantic queries (diagnostics, hover,
definition, references, symbols) over a ghūl project by driving the
compiler's analysis mode. Publishes `ghul.mcp`.

```sh
dotnet tool restore
dotnet build
./tests/smoke.sh
```

Protocol field names are made camelCase by a naming policy; don't rename
members by hand. Standard output carries protocol JSON only, and anything for
a human goes to standard error.

**`ghul-cli`** - a global .NET tool that runs `.ghul` scripts directly
(shebang lines included) and provides `ghul repl` and a Jupyter kernel.
Publishes `ghul.cli` and its sub-packages.

```sh
dotnet tool restore
dotnet build
dotnet test unit-tests
./tests/smoke.sh
./tests/jupyter.sh
```

Standard output belongs to the script being run: every subprocess the tool
starts for its own purposes has its output kept off it.

**`ghul-debug`** - a prototype VS Code debugger for ghūl built on netcoredbg.
Needs Node.js.

```sh
npm install
npm test
```

**`ghul-dashboard`** - a terminal dashboard of a local development machine's
ghūl work: test runs, worktrees and open pull requests. Not published.

```sh
dotnet tool restore
dotnet build ghul-dashboard.ghulproj
dotnet test tests
```

## Documentation and examples

**`ghul-dev`** - the [ghul.dev](https://ghul.dev) website, built with
VitePress. Needs Node.js. Deployed on merge to `main`.

```sh
npm ci
npm test
npm run build
dotnet tool restore
dotnet ghul-test --runtime-dll <path to the pinned ghul-runtime.dll> example-tests
```

The runtime passed to the example tests is the version pinned in
`example-tool/Directory.Packages.props`. Examples are written without
end-of-line semicolons, and CI fails on a `;` a line break would have inferred.
The pages display captured output, hovers and diagnostics, so after a compiler
or runtime version change the example data is regenerated with
`dotnet run --project example-tool -- examples src/.vitepress/example-data`.
Read that command's output for `[error]` lines: it exits successfully whether
or not every example compiled. Prose and examples follow the style guide in
`ghul-lang/ghul-style`.

**`ghul-examples`** - example programs, meant to be opened in a Codespace or
dev container.

```sh
dotnet tool restore
dotnet build
dotnet ghul-test --use-dotnet-build integration-tests
```

Example sources under `examples/` are symlinked into matching
`integration-tests/<example>/` directories: keep the links when editing, and
give a new example its test directory. The `GHUL.md` here is a synced copy of
the compiler's; refresh it by copying, never edit it here. Follows the style
guide in `ghul-lang/ghul-style`.

**`ghul-rosetta-code`** - ghūl solutions to [Rosetta Code](https://rosettacode.org)
tasks, each a runnable project under `tasks/<slug>/` with an output-checking
test. Merges through a merge queue.

```sh
dotnet tool restore
dotnet run --project tasks/<slug>
dotnet ghul-test --use-dotnet-build tasks/<slug>
dotnet ghul-test --use-dotnet-build tasks        # all of them
scripts/check-width.sh --hard
```

Read its `AGENTS.md` first. Every task has a `task.json` and a
`run.expected` captured with `scripts/capture.sh` only after the output has
been checked by hand; a task that does not build is never captured. Task
states are changed through the `tools/rosetta` tool, never by editing
`task.json`. Lines stay within 64 columns, and never past 76. Posting to the
Rosetta Code wiki is not part of any change in this repository.

To test a compiler change against these tasks, install that compiler into the
repository's tool manifest. `ghul-test`'s `--compiler` option has no effect
here: it prints the compiler it was given, then builds every task with the
pinned one.

**`ghul-playground`** - the browser playground and REPL at
[ghul.dev/playground](https://ghul.dev/playground/), which compile on a server
and run in the browser under WebAssembly. Deployed on merge to `main`.

```sh
dotnet workload install wasm-tools
dotnet tool restore
npm install               # also stages the Monaco editor
dotnet run --project web -c Release
```

Needs Node.js 22 or later and the `wasm-tools` workload. Build in Release: a
Debug WebAssembly build fails at start-up. CI runs a long list of Node test
scripts and a browser end-to-end test; see `.github/workflows/build.yml`.
Programs run in the browser on purpose: the server compiles code but never
runs it. Changes to the service configuration, the container setup or the
workflows are for the maintainer to approve.

**`ghul-web-api`** - an example ASP.NET Core web API written in ghūl.

```sh
dotnet tool restore
dotnet build ghul-web-api.ghulproj
dotnet build tests/smoke-test
tests/run-smoke.sh
```

**`ghul-repository-template`** - a GitHub template for starting a new ghūl
project, with a dev container and CI already set up.

**`ghul-scratchpad`** - a one-file project for trying the language. Its CI
always builds with the latest published compiler. It has no automated
reviewer and needs no review approval to merge.

## Supporting repositories

`create-version` (the action that allocates release versions),
`ghul-code-review` (the automated review workflow), `ghul-coverage-report`,
`ghul-renovate` (dependency update configuration), `ghul-templates`
(`dotnet new` templates) and `ghul-style` (the style guide for human-facing
content).

## Changes across repositories

A change that crosses repositories is one pull request per repository, using
the same branch slug in each. The order follows the dependencies: the compiler
or runtime first, then what consumes them. A consumer can only use a compiler
or runtime change once it has been published.
